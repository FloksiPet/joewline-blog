# ТЗ: система публікацій — від нотатки до трьох майданчиків

> Другий допис. Перший був про ідею — навіщо це все. Цей — про те, як воно влаштоване і чому саме так, а не інакше. Документ одночасно є і технічним завданням для реалізації, і поясненням логіки для читача, тому кожен розділ відповідає не тільки «що робити», а й «чому саме це».

## 0. Контекст

Я соло-розробник, який працює в кількох напрямках одночасно (мікроконтролери, іграшки на залізі, автоматизація через ШІ). Текст, який я хочу лишати після себе, народжується хаотично: голосом у Telegram, у чаті з ШІ під час рішення задачі, прямо у файлі поруч із кодом. Мета — щоб ця хаотичність не була проблемою, а ядро (я і мій досвід) віддзеркалювалось на кількох майданчиках без ручного дублювання роботи.

## 1. Чому взагалі система, а не «просто писати»

Три причини:

1. **Тертя вбиває звичку.** Якщо кожна нотатка вимагає окремого рішення «куди її нести і як форматувати», вона просто не буде написана. Тому вхід має бути один і максимально дешевий, а розподіл — автоматичний.
2. **Аудиторії не перетинаються, а формат — той самий.** Той самий шматок досвіду може бути сирою думкою для мого сайту й завершеним кейсом для DOU. Різниця не в контенті, а в **ступені готовності**. Отже, система має вміти розрізняти стадії, а не вимагати писати одне й те саме двічі.
3. **Я хочу володіти джерелом правди.** Соцмережі та платформи — це вітрини, а не сховище. Якщо DOU чи Друкарня завтра зникнуть або зміняться, мій архів має лишитись при мені. Тому ядром системи є git-репозиторій, а не будь-яка стороння платформа.

## 2. Принципи

- **Одна точка входу, багато виходів.** Незалежно від того, де народилась думка (голос, чат з ШІ, файл у проєкті), вона потрапляє в один репозиторій.
- **Готовність — це стан файлу, а не окремий текст.** Один і той самий файл дозріває: чернетка → розібраний кейс → готова стаття. Куди він може піти, залежить від стану, а не переписується вручну під кожен майданчик.
- **ШІ редагує, я вирішую.** ШІ виправляє орфографію, структурує, підказує формулювання. Але не пише текст «з нуля» замість мене (це не тільки моя перевага — це ще й жорстка вимога DOU, див. розділ 5).
- **Міцний фундамент, не саморобка з нуля.** У технічній основі — перевірені, широко використовувані інструменти (генератор сайту, GitHub Pages, GitHub Actions), а не власний велосипед. Гнучкість і кастомізація — зверху, а не замість фундаменту.
- **Автоматизація — там, де вона реально можлива.** Не всюди. Дослідження нижче показало, що DOU і Друкарня не мають публічного API — і це чесно враховано в архітектурі, а не проігноровано.

## 3. Формат «кейсу»

Кожен файл — markdown з frontmatter (метадані на початку файлу), які визначають, що з ним можна робити далі.

```yaml
---
title: "Коротка назва"
date: 2026-08-01
status: draft        # draft | in-progress | done
tags: [мікроконтролери, вайб-кодинг]
targets: [site]       # site | site,dou | site,dou,drukarnia
canonical: true        # чи цей файл — оригінал (а не крос-пост)
---
```

Тіло файлу — вільна структура, але для «кейсу» (у моєму розумінні — проблема + шлях розбору + рішення) є рекомендований скелет:

```markdown
## Проблема
Що не працювало / яке питання виникло.

## Хід розбору
Кроки, гіпотези, що відкидав і чому. Це можна лишити навіть без фіналу —
цінність саме в ході думки, а не тільки в результаті.

## Рішення
Що спрацювало і чому саме так.
```

Файл без секції «Рішення» — це нормальний матеріал для власного сайту (журнал процесу). Файл з усіма трьома секціями і статусом `done` — кандидат на DOU.

## 4. Ланцюг: від нотатки до публікації

### Етап 1 — Вхідні канали
Оскільки текст народжується по-різному, потрібен не один інтерфейс, а кілька входів в одну точку:
- **Telegram-бот собі** — приймає голосове чи текстове повідомлення, розшифровує голос (Whisper або аналог), кладе чернетку файлу в репозиторій.
- **Чат з ШІ** — коли думка вже оформлена в розмові з Claude/ChatGPT, прошу одразу зберегти її у форматі кейсу і закомітити.
- **Файл у проєкті** — нотатка пишеться просто поруч із кодом, а скрипт-помічник переносить її в репозиторій блогу.

*Чому саме так:* єдина вимога до кожного каналу — на виході має бути markdown-файл з правильним frontmatter. Сам канал не важливий, важливий контракт.

### Етап 2 — Git-репозиторій як джерело правди
Усі файли лежать в одному репозиторії. Це дає версійність (видно, як текст змінювався), незалежність від платформ і можливість у будь-який момент перенести сайт на інший хостинг без втрати архіву.

### Етап 3 — Генератор сайту + GitHub Pages
Генератор сайту (Astro або Hugo — обидва зрілі, широко протестовані інструменти з великими спільнотами) перетворює папку markdown-файлів на статичний сайт. GitHub Pages хостить його безкоштовно.

*Чому статичний генератор, а не CMS з базою даних:* немає що адмініструвати, немає що зламати, немає бюрократії «увійти в адмінку». git push — і сайт оновився.

### Етап 4 — Автоматична збірка та деплой
GitHub Actions (сценарій, що спрацьовує на push) перезбирає сайт і публікує його автоматично при кожному коміті в основну гілку.

### Етап 5 — Розподіл по майданчиках
Тут я спеціально перевірив, що реально можна автоматизувати, а що ні (див. розділ 5) — і архітектура нижче будована під реальні обмеження, а не під бажану картинку.

| Майданчик | Спосіб публікації | Рівень автоматизації |
|---|---|---|
| Власний сайт | git push → build → deploy | Повна автоматизація |
| Telegram-канал (анонс) | Bot API, повідомлення з посиланням при виході нового посту | Повна автоматизація |
| DOU | Форма на сайті, вручну | Автоматизується лише підготовка тексту, публікація — руками |
| Друкарня | Редактор на сайті, вручну, але з підтримкою Markdown | Автоматизується підготовка, вставка — руками, з мінімальним форматуванням |

### Етап 6 — Псевдонім і візуальна ідентичність
Контент публікується під псевдонімом **JoeWline (JWL)** — окремо від технічного GitHub-акаунту `floksipet`, який лишається робочим/пет-проєктним. Розділення навмисне: `floksipet` — це де я тримаю код, `JoeWline` — це публічне обличчя думок і кейсів. Технічно це не заважає одне одному: репозиторій блогу може жити хоч під `floksipet`, хоч під окремим акаунтом — GitHub Pages не вимагає збігу імені акаунту з публічним брендом.

## 5. Що показало дослідження майданчиків (важливо, чесно)

Перш ніж писати «автоматично публікується всюди», я перевірив реальні можливості DOU і Друкарні. Ось що виявилось:

**DOU не має публічного API.** Кілька років тому редакція спростила процес — тепер матеріал можна подати самостійно через форму на сайті, без листування з редактором. Але це форма для людини, а не програмний інтерфейс: автоматизувати сам факт публікації неможливо.

Ще важливіше — правила форуму напряму зачіпають мій підхід:
- Матеріал не повинен був публікуватись раніше ніде — окрім одного винятку: якщо він уже виходив у власному блозі автора. Тобто крос-постинг зі свого сайту на DOU офіційно дозволений, схема з canonical-посиланням тут законна, а не сіра зона.
- Пряме написання тексту статті за допомогою ШІ забороняється. Дозволено використовувати ШІ для допомоги з ідеями та для редагування вже написаного людиною тексту.

Це не перешкода, а фактично підтвердження мого власного принципу з розділу 2 — ШІ в мене і так відповідає за структуру, орфографію, редагування, а не за авторство тексту. Обмеження DOU і мій робочий процес збігаються самі собою. Додатково DOU встановлює доволі високу нижню межу обсягу — це природно відсікає сирі нотатки: на DOU підуть тільки файли зі статусом `done`.

**Друкарня теж не має публічного API для розробників.** Технічно платформа побудована на Nuxt, а редактор розуміє Markdown і вміє підсвічувати код — це дещо полегшує ручний крос-пост, готовий markdown-файл вставляється майже без переформатування. Але сама дія публікації — це так само клік людини у браузері, а не виклик API.

**Висновок для архітектури:** повна автоматизація можлива тільки для власного сайту й Telegram-анонсів. Для DOU і Друкарні реалістична мета — не «натиснув кнопку і скрізь опублікувалось», а «файл вже повністю готовий у форматі, який лишається скопіювати за 30 секунд». Це і закладено у схему розподілу вище.

## 6. Що зробити на компʼютері (чекліст реалізації)

1. Створити git-репозиторій для блогу.
2. Розгорнути шаблон Astro або Hugo, підключити до GitHub Pages.
3. Створити шаблон кейсу (frontmatter + скелет секцій із розділу 3) як файл-заготовку.
4. Написати/вайбкодити Telegram-бота: приймає голос/текст, розшифровує, комітить чернетку у репозиторій.
5. Налаштувати GitHub Action: build + deploy при push у основну гілку.
6. Налаштувати Telegram-канал і бота для автоматичного анонсу нового посту (посилання зі свіжим слагом).
7. Зареєструвати профілі на DOU і Друкарні під псевдонімом JoeWline, оформити біо з посиланням на власний сайт.
8. Додати лого/аватар JWL на всі майданчики (окремий файл нижче).
